# M2.3 — BotLogic remote validation before activation

**M2.3 — PASS.**

Engo's explicit BotLogic policy deployment now follows this invariant:

1. local policy-file preflight;
2. non-mutating validation by the configured BotLogic instance through `POST /v1/validate`;
3. activation of the exact same source through `POST /v1/consult`.

The client encodes steps 2–3 in `ValidateAndConsult`. Tests verify the HTTP ordering and verify that a failed validation never reaches consult.

This means a policy requested for deployment cannot replace the active BotLogic ruleset unless that BotLogic instance first accepts the source in its non-mutating validation interpreter.

The explicit deployment remains startup-fail-closed. Optional runtime BotLogic operation remains standalone-friendly and fail-open according to the existing integration policy.
